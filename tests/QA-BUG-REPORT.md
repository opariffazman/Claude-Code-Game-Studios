## Critical Bugs (S1) — Must fix before any build ships

| ID | Severity | File:Line | Description | Suggested Fix |
|----|----------|-----------|-------------|---------------|
| BUG-001 | S1 | `src/systems/rebuild-cycle.ts:73–76` | **Overlay Graphics is statically sized (4000×3000) and will fail to cover larger viewports.** The overlay rect is hard-coded to `rect(-200, -200, 4000, 3000)`. On a 4K or ultrawide display the right or bottom edge will be visible during the fade-to-white transition, exposing the desktop rebuilding underneath. This is a visual-safety regression: the flash transition is a WCAG-adjacent feature and a partial flash is worse than none. | Replace the hard-coded dimensions with dynamic values based on `window.screen.width / height` at construction time, or use `window.innerWidth + 400` / `window.innerHeight + 400` and update on resize. Alternatively add a `resize(w, h)` method to `RebuildCycle` called from `DeskSmasherApp.onWindowResize()`. |
| BUG-002 | S1 | `src/effects/destruction-effects.ts` (multiple functions) | **setInterval-based animations are never cancelled if the element's container is destroyed or the desktop rebuilds mid-animation.** `bounce`, `inflatePop`, `pixelate`, `melt`, `gravityFlip`, and `vortex` all use `setInterval`. If `desktop.reset()` or `desktop.rebuildWithTheme()` is called while one of these is running (possible when the player triggers the last hit right at the celebration pause boundary), the interval callback fires against a destroyed container, attempting to mutate `container.y`, `container.scale`, `container.alpha`, etc. on a node that has been removed from the stage. PixiJS v8 does not guard against this, so it writes to stale objects — a silent data corruption / potential crash in some renderers. | All 6 effects are already annotated `// TODO: convert to ticker-driven`. Prioritise the ticker migration. Short-term mitigation: store each interval ID per-element (e.g. a WeakMap) and cancel all pending intervals at the start of `DesktopManager.reset()` / `removeChildren()`. |

## Major Bugs (S2) — Should fix before release

| ID | Severity | File:Line | Description | Suggested Fix |
|----|----------|-----------|-------------|---------------|
| BUG-003 | S2 | `src/desktop/desktop-manager.ts:31` | **Module-level `nextId` counter is never reset.** `nextId` is a module-scoped `let` that increments every element creation and never rolls back. After many desktop rebuilds (or if the module is reloaded in a dev/HMR context) element IDs grow without bound. More critically, `nextId` is not reset when `DesktopManager.reset()` is called, so element IDs are never recycled. This is benign at runtime (IDs are just used for Map lookups) but makes debugging harder and creates an unbounded memory path in `_dragDamageTimers` — old element IDs accumulate in the throttle Map since `resetDrag()` only resets the flag, not the Map. | Move `nextId` inside the `DesktopManager` class as a private instance field, or reset the `_dragDamageTimers` Map in `MouseToolManager.clearTrails()` which is already called on rebuild. |
| BUG-004 | S2 | `src/mouse/mouse-tool-manager.ts:64, 404–418` | **`_dragDamageTimers` Map grows unboundedly.** Entries are added on every drag hit (keyed by element id) but the Map is never pruned. After N rebuild cycles each with M elements, the Map holds N×M stale entries. There is no call to `_dragDamageTimers.clear()` anywhere. At 10+ rebuilds the Map can exceed hundreds of entries. | Call `this._dragDamageTimers.clear()` inside `clearTrails()`, which is already invoked by `DeskSmasherApp` on each rebuild. |
| BUG-005 | S2 | `src/audio/audio-manager.ts:84–95` | **Firefox resume listener is never removed if the AudioContext starts successfully on first call.** Two listeners are added to `document` (`'click'` and `'keydown'`) to resume a suspended AudioContext. The removal check only fires if `context.state === 'running'` — but if the context starts suspended and then gets resumed by the game's own `ensureContext()` call on a subsequent user gesture, the removal predicate is never checked and the listeners leak permanently. | Move the removal outside the `if (state === 'running')` block so both listeners are always removed once the context is no longer suspended, or use `{ once: true }` with an explicit guard on the state. |
| BUG-006 | S2 | `src/vfx/mouse-trail.ts:106–109` | **MouseTrail uses `window` coordinates but PixiJS stage uses canvas coordinates.** `_onMouseMove` receives `e.clientX / e.clientY` and passes them directly to `_spawnSparkle` which calls `gfx.position.set(x, y)` in stage space. `clientX/Y` is viewport-relative, not canvas-relative. When the canvas is not positioned at (0, 0) — e.g. on mobile with a top toolbar, or when the page is scrolled — the sparkles will appear at the wrong position. `InputManager` correctly uses `canvasPos(clientX, clientY)` to subtract the canvas rect; `MouseTrail` skips this step. | Apply the same `canvas.getBoundingClientRect()` subtraction that `InputManager.canvasPos()` uses, or accept pre-converted canvas coordinates from a higher level (pass the canvas element to `MouseTrail` constructor). |
| BUG-007 | S2 | `src/mouse/mouse-tool-manager.ts:112–113` | **MouseToolManager cursor also uses raw `clientX/Y`.** Same coordinate space mismatch as BUG-006: `_cursor.position.set(e.clientX, e.clientY)` positions the cursor Graphics node in PixiJS stage space using viewport coordinates. The cursor will drift from the actual pointer position whenever the canvas is not flush with the viewport origin. | Same fix as BUG-006: subtract canvas bounding rect offset from the raw client coordinates before setting position. |
| BUG-008 | S2 | `src/effects/damage-effects.ts:48–64` | **`damageShake` captures `container.x/y` as `origX/origY` at start time, then restores them on interval expiry. If physics moves the element during the 250 ms shake, the restore snaps the container back to its pre-shake position, overwriting the physics movement.** Specifically, `DesktopManager.update()` writes `c.x = el.x` / `c.y = el.y` every frame. The interval restore writes `container.x = origX` which then gets overwritten by the next physics frame. Net effect: no actual corruption, but the restore is always redundant and wastes CPU. More importantly, if two shakes are applied to the same element in quick succession (possible at chaos level 3), `origX/origY` is captured from the already-shaking container, so restoration positions are wrong. | Use a stable "rest position" stored in `DesktopElement.x/y` rather than the container's current `.x/.y`, since `DesktopElement` coordinates are the authoritative physics position. |
| BUG-009 | S2 | `src/systems/theme-system.ts:160–176` | **`getNextTheme()` weighted random selection has an off-by-one: the `chosen` variable is pre-set to `candidates[0]` but the loop body only updates `chosen` when `roll <= 0`. If all weights are equal (which they currently are — all `weight: 1`) the last candidate in the array is under-represented because the loop exits with `chosen = candidates[0]` whenever `roll` lands in the last candidate's bucket without reaching `<= 0`.** Actually re-examining: with equal weights `totalWeight = N-1`, the loop reduces `roll` by 1 each iteration. If `roll` never hits `<= 0`, the function returns `candidates[0]`, not the last candidate. This biases the selection away from the last theme. | Change the pre-initialisation to `candidates[candidates.length - 1]` as the default (last candidate wins if no earlier candidate matched), which is the standard weighted-random idiom. |

## Minor Bugs (S3) — Fix when capacity allows

| ID | Severity | File:Line | Description | Suggested Fix |
|----|----------|-----------|-------------|---------------|
| BUG-010 | S3 | `src/desktop/element-factory.ts:154–158` | **Window faux-content lines use `Math.random()` during `createWindow()`.** Content line widths are randomised at construction time, making the visual width vary on each rebuild. This is intentional for variety but means the content lines allocated in `ElementFactory` are different on every `reset()`. This is not a bug per se, but it means content lines are _not_ deterministic even for the same window title — making visual regression testing harder. | Document this as intentional, or seed the RNG per-window using the title string hash. |
| BUG-011 | S3 | `src/desktop/desktop-manager.ts:553` | **`buildNotifications` uses a hard-coded color array `[0x4488ff, 0x44cc44, 0xff8844, 0xcc44cc]` instead of a theme-aware color set.** Notification colors are never themed — they always cycle through the same 4 colors regardless of the active theme. | Add a `notificationColors` field to the `Theme` interface and pass it through `rebuildWithTheme`. |
| BUG-012 | S3 | `src/desktop/desktop-manager.ts:282–286` | **`crackWallpaper()` inserts marks at index 1 via `addChildAt`, but if the desktop container has only the wallpaper background (index 0) and no other children, `addChildAt(mark, 1)` inserts after index 0 correctly. However, after many cracks the check `this.container.children.length > 1` is always true even if those children include element containers, so crack marks can appear on top of element containers.** The logic correctly places cracks at index 1 (above wallpaper, below everything else) only initially. As element containers are added at higher indices this is still fine, but there is no cap on the number of accumulated crack marks — they grow forever until `reset()`. | Add a cap (e.g. 50 marks max) and recycle the oldest mark when the cap is exceeded, similar to the particle pool pattern already used elsewhere. |
| BUG-013 | S3 | `src/audio/audio-manager.ts:73, 178` | **Master volume is hard-coded to `0.7` in two places** (`ensureContext` line 73 and `toggleMute` line 178) rather than reading from `AUDIO_CONFIG` or `SAFETY_CONFIG.MAX_VOLUME`. If `SAFETY_CONFIG.MAX_VOLUME` is changed, these will diverge silently. | Replace both `0.7` literals with `this.safety.maxVolume` which already reads from `SAFETY_CONFIG.MAX_VOLUME`. |
| BUG-014 | S3 | `src/vfx/sprite-particles.ts:60–61` | **`POOL_SIZE`, `SCALE_MIN`, `SCALE_MAX`, `DEFAULT_SPEED`, `DEFAULT_GRAVITY`, `DEFAULT_LIFE`, and `DEFAULT_SPREAD` are file-local constants not exposed through `PARTICLE_CONFIG` or any config file.** This violates the project coding standard: "Gameplay values must be data-driven (external config), never hardcoded." | Move `SpriteParticles` constants into `PARTICLE_CONFIG` in `src/config.ts`. |
| BUG-015 | S3 | `src/systems/rebuild-cycle.ts:25–29` | **`CELEBRATE_DURATION`, `FADE_OUT_DURATION`, and `FADE_IN_DURATION` are file-local constants not in `config.ts`.** Same config standard violation as BUG-014. | Add a `REBUILD_CONFIG` block to `src/config.ts`. |
| BUG-016 | S3 | `src/desktop/desktop-manager.ts:339–343` | **Physics edge-bounce uses `this.screenH - taskbarH` as the floor, but after an impulse `el.y + el.height` can momentarily exceed the floor before the next `update()` tick corrects it.** Specifically `el.y` is set to `this.screenH - taskbarH - el.height` but the container `c.y` is then set to `el.y`. Since `el.x` and `el.y` represent the top-left corner and `el.width`/`el.height` represent the bounding box dimensions, this is correct only if the container's anchor is at (0,0). PixiJS containers default to (0,0) anchor so this is fine — but the same pattern for the right-edge bounce `el.x = this.screenW - el.width` can produce negative x if `el.width > this.screenW`. | Add a guard: `if (el.width > this.screenW) skip bounce correction`. |
| BUG-017 | S3 | `src/app.ts:222` | **`window.addEventListener('resize', ...)` is never removed.** The resize listener is added in `start()` but there is no `destroy()` method on `DeskSmasherApp` and the listener is never cleaned up. For a long-lived single-page app this is harmless, but it leaks if `start()` is ever called more than once (e.g. in tests). | Add a `destroy()` method to `DeskSmasherApp` that removes the resize listener and calls `destroy()` on `inputManager`, `mouseTools`, `mouseTrail`, `audioManager`, and `particles`. |
| BUG-018 | S2 | `src/app.ts:205` | **Drag handler calls `hitElement()` (random effect) instead of `hitElementToolAware()`, so any click with micro-mouse-movement produces random visual effects regardless of the selected tool.** The `onDrag` callback at line 201–207 feeds drag-hit elements into `this.hitElement(el)` — the keyboard-path function that picks a random effect from `destructionRegistry.getRandom()` or `damageRegistry.getRandom()`. The drag path activates as soon as cursor movement exceeds `INPUT_CONFIG.DRAG_THRESHOLD_PX`; natural hand tremor during a normal click routinely crosses this threshold, so `dragActive` becomes true and `emitInput({type:'click'})` is never emitted. The element is then hit via the drag handler using `hitElement` (random effects) rather than the click handler using `hitElementToolAware` (tool effects). The click path (`handleMouseHit` → `hitElementToolAware`) is only reached for perfectly stationary clicks. | Change line 205 from `this.hitElement(el)` to `this.hitElementToolAware(el)`. The drag handler already has access to `hitElementToolAware` — the fix is a one-word substitution. |

## Code Quality Issues

| ID | Category | File:Line | Description | Suggested Fix |
|----|----------|-----------|-------------|---------------|
| CQ-001 | Dead field | `src/desktop/desktop-manager.ts:57–58` | `_lastTheme` is assigned in `ThemeSystem.getNextTheme()` but never read anywhere. | Remove the `_lastTheme` field from `ThemeSystem` if it has no planned use, or document its intended purpose. |
| CQ-002 | TODO backlog | `src/effects/destruction-effects.ts` and `src/effects/damage-effects.ts` | **10 `setInterval`-based animations are tagged `// TODO: convert to ticker-driven`** but remain as is. These will cause jank at non-60 fps (the hardcoded `0.016` time step assumes exactly 60 fps), produce incorrect animations at high frame rates (165 Hz monitors), and run at wrong speeds on throttled devices. | Convert all animation loops to use the PixiJS ticker via a small `AnimationScheduler` utility that stores pending callbacks and executes them in `app.ticker.add`. |
| CQ-003 | Config violation | `src/mouse/mouse-tool-manager.ts:29–42` | `MOUSE_TOOL_CONFIG` is a file-local const object inside `mouse-tool-manager.ts` rather than in `src/config.ts`. Multiple tool configs (`HAMMER_CONFIG`, `LASER_CONFIG`, etc.) are similarly isolated per file. | Either centralise all tool config into `MOUSE_TOOL_CONFIG` in `src/config.ts`, or document the per-tool-file pattern as intentional in the architecture notes. |
| CQ-004 | Memory / allocation | `src/desktop/desktop-manager.ts:129–132` | **`getRandomAlive()` allocates a new filtered array on every call.** This is called on every keyboard hit (up to 13+ times/second at chaos level 3). | Pre-allocate a reusable scratch array or compute the random alive element in a single loop without `filter()`: iterate the elements once, using reservoir sampling. |
| CQ-005 | Safety gap | `src/vfx/particle-manager.ts:220–222` | **`emit()` records one flash event for any burst `> 5` particles, but does not scale the flash count with the actual burst size.** A single `emit(x, y, 300, ...)` call records only one flash event even though it produces a very bright burst. At chaos level 3, `handleKeyboardHit` calls `emit` with `chaosLevel * 5 = 15` extra particles on top of the destruction burst — each individually checks `canFlash()` but the total visual brightness is not accurately modelled. | Consider recording a flash proportional to burst size when count is large (e.g. `Math.ceil(count / 10)` flash events), subject to the budget check. This is a conservative safety improvement, not a WCAG violation in current form. |
| CQ-006 | Error handling | `src/audio/audio-manager.ts:203–220` | **`preloadSounds()` sets `this.soundsPreloaded = true` before awaiting all load promises.** If the function is called a second time while the first load is still in progress (possible if `ensureContext()` has not yet returned but a second user gesture fires `audioStarted = false` reset — not currently possible but fragile), the second call would see `soundsPreloaded = true` and return early, leaving the first load incomplete with no retry. | Set `soundsPreloaded = true` only after `await Promise.all(loadPromises)` completes. Use a separate `_loading: Promise<void> | null` field to guard concurrent calls. |
